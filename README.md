# MAX ⇄ Telegram Bridge v2.2 — Multi-Account, Invites, Backups & Tests

Мост между веб-клиентом мессенджера **MAX** (`https://web.max.ru`) и
**Telegram** для школьных чатов. Версия 2.0 переносит управление аккаунтами
и правами **внутрь Telegram-бота**: админ добавляет аккаунты MAX, ведёт
интерактивную авторизацию (со скриншотами страницы прямо в чат бота),
назначает Владельцев и Слушателей — без консоли, файлов конфигов и рестартов.
Версия 2.1 добавляет **инвайт-ссылки (deep linking)**: слушатель или владелец
подключается сам, по клику — админу больше не нужно выспрашивать числовой
`tg_user_id`.


### Что нового в 2.0

| Возможность | Как |
|---|---|
| **2–5 изолированных аккаунтов MAX** | у каждого свой `launch_persistent_context` в `/data/profiles/account_<id>/`, свой Chromium-процесс и свой набор asyncio-задач |
| **Роли** (SQLite) | Супер-админ (`ADMIN_TG_ID`), **Владелец** аккаунта (1-к-1, двусторонняя связь), **Слушатели** (read-only) |
| **Фан-аут сообщений** | каждое сообщение MAX уходит в ЛС Владельцу и каждому Слушателю; для каждого — своя запись `message_map`, поэтому reply Владельца резолвится именно в свой исходник |
| **Авторизация через бота (FSM)** | добавление/переавторизация аккаунта прямо в диалоге с ботом; после телефона и кода бот шлёт **скриншот страницы** — сразу видно, капча или код принят |
| **Уведомления о севших сессиях** | ночью сессия протухла → админу сообщение с кнопкой «🔑 Переавторизовать <имя>», той же кнопкой стартует FSM поверх сохранённого профиля |
| **Изоляция отказов** | падение/разлогин одного аккаунта не касается остальных; авто-перезапуск с backoff |
| **Разнесённые ночные перезагрузки** | аккаунт N стартует мягкий reload в `03:00 + N*7 минут` |

Сетевая идеология v1 сохранена: **MAX — всегда напрямую** (резидентный IP —
«обычный юзер», дата-центровый прокси = флаг антифроду); **Telegram — только
через `TG_API_BASE`** (`TelegramAPIServer.from_base` + собственный Nginx).

## 2. Ролевая модель

| Роль | Кто | Права |
|---|---|---|
| **Супер-админ** | `ADMIN_TG_ID` из `.env` (единственный) | `/admin`: добавлять/запускать/останавливать/удалять аккаунты, вести авторизацию, назначать владельцев и слушателей, статус системы. Сам может одновременно быть и владельцем/слушателем аккаунтов |
| **Владелец** | `accounts.owner_tg_id`, ровно один на аккаунт | получает всё из чата MAX в ЛС; **может отвечать**: reply на пересланное (уходит реплеем/цитатой в MAX) или `!макс текст`; фото — приложением |
| **Слушатели** | строки таблицы `listeners` | только чтение: получают копию входящих; на их попытки отвечать — вежливая заглушка «у вас режим только чтение» (не чаще раза в 5 минут) |

Правило ответа: reply резолвится через `message_map(tg_message_id)` →
аккаунт + превью исходника; отвечать может только `owner_tg_id` этого
аккаунта. У владельца с несколькими аккаунтами `!макс …` спрашивает,
в какой из них отправить (inline-кнопки).

> даёт `exec /bin/sh: exec format error` (контейнер тянет arm64-бинарники без
> эмуляции). Варианты:
> - **разработка/отладка на x86:** `BRIDGE_PLATFORM=linux/amd64 docker compose up -d --build`
>   (базовый Playwright-образ мультиарх, всё нативно; том `data/` переносим на плату потом);
> - **собрать arm64-образ на x86 для переноса:** один раз
>   `docker run --privileged --rm tonistiigi/binfmt --install arm64`, затем
>   `docker buildx build --platform linux/arm64 -t max-tg-bridge:2 --load .`.

Nginx-реверс Telegram API — как в v1, конфиг в
[`nginx/telegram-api.conf.example`](nginx/telegram-api.conf.example)
(проксируются `/bot…` и `/file/bot…`, `proxy_ssl_server_name on`,
`Host: api.telegram.org`).

### 3.1. Два эндпоинта прокси: `/bot` и `/file` — не путать

Bot API отвечает на **два разных пути**, и мост пользуется обоими:

| Путь | Что делает | Где используется |
|---|---|---|
| `/bot<token>/<method>` | все вызовы API: `sendMessage`, `getUpdates`, `getFile`, **загрузка** фото/документов (`UploadFile` идёт сюда же) | постоянно |
| `/file/bot<token>/<path>` | **скачивание** файлов, которые прислали вам (фото Владельца → MAX) | только `extract_photo` |

Типичная дыра: проксируют только `location /bot`, а `location /file` забывают —
тогда мост выглядит полностью рабочим (текст ходит в обе стороны, скриншоты
админа доезжают), но **фото из Telegram молча теряются**. С v2.2.1 это не молчание:

* при старте бот пробует оба эндпоинта и пишет в лог `✓ Прокси /bot отвечает` /
  `⚠ Эндпоинт /file НЕ проксирует Telegram API`;
* владелец, приславший фото при нерабочем `/file`, получает объяснение
  (не чаще раза в 10 минут), а не бесконечное ожидание;
* проба использует **ту же сессию, что и транспорт** — с учётом `TG_PROXY_URL`,
  иначе она ходила бы мимо прокси и врала.

**Свой Nginx:** добавьте второй `location`, как в
[`nginx/telegram-api.conf.example`](nginx/telegram-api.conf.example) (блок
`# --- файлы: /file/bot<token>/<path> ---`).

**Сторонний ретранслятор** (`TG_API_BASE` вида `https://host/ключ`, например geoctx):
пути раздаёт сервис, а не вы. Проверьте в его документации, проксирует ли он
`/file`; если нет — фото из Telegram недоступны **по вине прокси**, и лечится
это только сменой прокси или своим Nginx. Текст при этом работает.

Отличить одно от другого помогает лог старта: если `sendMessage`/`getUpdates`
тоже валятся по таймауту — проблема в `/bot` (сам ретранслятор медленный или
нестабильный), а не в отсутствии `/file`.

Первый запуск без аккаунтов: бот жив, `/admin` показывает пустую панель.

## 4. Первый аккаунт — из Telegram, без консоли

1. Админ пишет боту `/admin` → **➕ Добавить аккаунт MAX**.
2. Бот спрашивает по очереди:
   - **имя профиля** («Школа 5Б»);
   - **название чата в MAX** (можно и прямую http-ссылку на чат);
   - **Telegram ID Владельца** (число или `me` = сам админ).
3. Бот создаёт аккаунт, поднимает изолированный Chromium, открывает
   `web.max.ru` и просит **номер телефона** — админ присылает его в чат.
4. Бот вводит номер, жмёт «Далее» и **присылает скриншот страницы**: видно,
   что кодовое поле появилось / вылезла капча / уехал QR.
5. Админ присылает **код из СМС** → бот вводит → снова скриншот → бот ждёт
   входа (до 90 c), открывает целевой чат по названию, закрывает браузер
   входа, помечает аккаунт 🟢 и поднимает воркер. Готово — сообщения пошли
   Владельцу в ЛС.
6. Слушатели: `/admin → аккаунт → 🔗 Создать инвайт-ссылку` (быстрее всего —
   человек подключится сам, его `full_name`/`@username` запишутся автоматически)
   либо `👥 Слушатели → ➕` и «`123456789 Папа Маши`» (ручной ввод по ID, как в v2.0).

Ввод «отмена» на любом шаге аккуратно сворачивает сессию (новый аккаунт
полностью откатывается; переавторизация оставляет аккаунт в 🔴).

### Капча / QR

Если после телефона или кода на скриншоте видна капча/QR, бот даёт кнопку
инструкции и «Повторить код». Автоскрипт картинки не разгадывает.
Чтобы пройти её глазами:

1. В `docker-compose.yml` раскомментируй Xvfb/VNC-блок (`entrypoint:
   ["/usr/local/bin/xvfb-start.sh"]`, `VNC_ENABLE=1`, порт `127.0.0.1:5900`),
   поставь `.env` `MAX_HEADLESS=false`.
2. `docker compose up -d bridge`, повтори «Переавторизовать» в боте.
3. `ssh -L 5900:127.0.0.1:5900 pi@опи` → VNC-клиент на `localhost:5900`
   (пароль из `VNC_PASSWORD`) — перед глазами настоящий Chromium, проходится
   мышкой. После — вернуть compose в боевой вид.
   (Альтернативы: noVNC-контейнер; `ssh -X` с пробросом X11-сокетов — см. ниже
   «Отладка».)

### Севшая сессия ночью

Воркер любого аккаунта при детекте разлогина: статус `auth_required`,
уведомление админу «🔴 Сессия MAX аккаунта <имя> истекла» + кнопка
**«🔑 Переавторизовать»** → тот же FSM, но профиль (`data/profiles/account_N`)
сохранён: обычно достаточно свежего кода из СМС, телефон спрашивается только
при редком полном сбросе. Остальные аккаунты работают как ни в чём не бывало.

### Аварийный консольный вход (если Telegram-канал сам недоступен)

## 5. Миграция с v1

```bash
# 1) обновить код до v2, .env дополнить ADMIN_TG_ID;
#    старые строки TG_CHAT_ID / MAX_CHAT_TITLE / MAX_CHAT_URL / MAX_SELF_NAME
#    ВРЕМЕННО оставить — скрипт использует их как сид первого аккаунта
docker compose run --rm bridge python scripts/migrate_v1.py --dry-run
docker compose run --rm bridge python scripts/migrate_v1.py
docker compose up -d --build
```

Скрипт идемпотентен и делает три вещи:

1. **SQL** (`store.py` сам, при открытии базы v1): `seen_message`/`msg_map`
   переносятся в «аккаунт-наследник №1» (схема —
   [`migrations/0002_role_based_multiaccount.sql`](migrations/0002_role_based_multiaccount.sql));
2. **ENV-сид**: имя/чат/владелец/анти-эхо аккаунта из строк v1
   (`TG_CHAT_ID` становится Владельцем; групповой чат v1 → id личного
   аккаунта менять не надо, просто добавьте нужных людей слушателями);
3. **Файлы**: `data/chrome_profile/` переезжает в
   `data/profiles/account_1/` — живая сессия MAX сохраняется; сообщения
   пойдут сразу, авторизация обычно не требуется вовсе.

После проверки удалите legacy-строки из `.env`. Ответы из старого общего
чата v1 не мигрируют: reply-маппинг привязан к личным диалогам v2.

## 6. Схема БД (v2.1, user_version=3)

```sql
accounts(id, name UNIQUE, phone, max_chat_title, max_chat_url, max_self_name,
         owner_tg_id, status, profile_path, created_at, updated_at)
listeners(id, account_id FK→accounts ON DELETE CASCADE, tg_user_id, alias,
          username NULL, full_name NULL,          -- v2.1: из инвайта
          created_at, UNIQUE(account_id, tg_user_id))
invites(id, token UNIQUE, account_id FK ON DELETE CASCADE,
        role 'listener'|'owner', max_uses (0=∞), used_count,
        expires_at NULL=бессрочно, created_at)    -- v2.1
message_map(id, account_id FK, tg_user_id, tg_message_id UNIQUE,
            max_message_key, max_sender, max_preview, created_at)
seen_message(account_id, key, first_seen, PRIMARY KEY(account_id, key))
stats(account_id, name, value, PRIMARY KEY(account_id, name))
meta(k, v)
```

`message_map` — критичная таблица фан-аута: один текст из MAX порождает N
telegram-сообщений (Владелец + Слушатели), у каждого свой `tg_message_id`;
именно поэтому ключ карты — **на** сообщение от бота, а владелец резолвится
по нему обратно к `max_message_key` и превью для реплея в MAX.

Миграция 2→3 выполняется автоматически при старте (`store.py`): создаётся
`invites`, к `listeners` добавляются nullable-колонки `username`/`full_name`
— строки v2.0, добавленные вручную по ID, остаются валидными (NULL вместо
имени). Справочный SQL:
[`migrations/0003_invites.sql`](migrations/0003_invites.sql).

## 8. Инвайт-ссылки (v2.1)

### Создание (админ)

`/admin → аккаунт → 🔗 Создать инвайт-ссылку` → выбрать роль и лимит.
Бот генерирует криптостойкий токен (`secrets.token_urlsafe(16)`) и отдаёт
ссылку `https://t.me/<BOT_USERNAME>?start=inv_<token>` — её можно сразу
переслать человеку в любой чат/ЛС. `BOT_USERNAME` берётся из `get_me()`
при старте (через ваш Nginx-прокси — никаких дополнительных запросов).
Если у бота нет `@username` (технический токен), бот отдаст сам токен и
попросит человека ввести `/start inv_<token>` вручную.

Типы ссылок:

| Тип | max_uses | expires | Смысл |
|---|---|---|---|
| Одноразовая | 1 | — | один человек, потом ссылка мертва |
| На 5 человек | 5 | — | родительский комитет «оптом» |
| Безлимитная | 0 | — | ссылкой можно расписаться в самом чате MAX |
| 24 часа | 1 | +24 ч | забыли/не успели — утром протухнет само |
| Владелец | **всегда 1** | — | привязка основного пользователя; повторная ссылка не выдаётся, действующий владелец при активации замещается |

### Активация (пользователь)

Человек открывает ссылку → Telegram показывает кнопку «Запустить»
(`/start inv_<token>`) → бот атомарно проверяет и «списывает» токен:

* невалидный/отозванный/исчерпанный/просроченный →
  «Ссылка недействительна или срок её действия истёк. Запросите новую у
  администратора»;
* слушатель → запись в `listeners` с `full_name`/`@username` из
  `message.from_user`, приветствие с описанием прав чтения;
* владелец → `accounts.owner_tg_id = <id>`, приветствие с инструкцией
  по ответам (reply/префиксы);
* админ получает пуш: «✅ Пользователь Иван Иванов (@ivanov, ID: 12345678)
  подключился по инвайт-ссылке как Слушатель к аккаунту «Школа 5Б»» +
  остаток активаций ссылки.

### Защита от гонки

Активация — одна транзакция `BEGIN IMMEDIATE` с guarded-инкрементом:

```sql
UPDATE invites SET used_count = used_count + 1
 WHERE token = ?
   AND (expires_at IS NULL OR expires_at > :now)
   AND (max_uses = 0 OR used_count < max_uses)
   AND (role <> 'owner' OR used_count = 0);
```

`rowcount = 0` → «exhausted»/«expired» (сверка по свежему SELECT).
Шесть параллельных потоков по одноразовой ссылке дают ровно один успех —
это покрыто офлайн-проверкой (см. §9).

### Управление ссылками

`🎟 Активные инвайты` — только живые (неисчерпанные и непросроченные),
с остатком активаций и сроком; кнопка «🚫 отозвать» удаляет ссылку
до использования. При удалении аккаунта его инвайты каскадно стираются.
Отключённый слушатель получает уведомление «вы отключены от рассылки».

## 9. Как пользоваться Владельцу/Слушателю

| Действие | Кто | Результат |
|---|---|---|
| Сообщение в чате MAX | все получатели | в ЛС: `👤 Мария Ивановна · 12.11 15:03` + текст; фото — подписанным `send_photo` (до 4 шт., последовательно) |
| **Reply** боту на сообщение из MAX | только Владелец аккаунта-источника | в MAX: «ответ» на исходное сообщение (best-effort меню) или цитата «…» + ответ |
| `!макс текст` / фото с префиксом | только Владелец | обычное сообщение в MAX (при нескольких аккаунтах — кнопка выбора) |
| Любой ответ | Слушатель | «у вас режим только чтение» (throttled) |
| 🔗 Инвайт-ссылка | кто угодно | сам подключается: слушателем или владельцем, id не спрашивает |
| `/start`, `/id`, `/help` | все | свои роли и id |

Эхо-защита от петли: собственные сообщения не пересылаются (mine-маркеры,
`max_self_name`, окно хэшей исходящих 90 с).

## 10. Резервные копии (v2.2)

### Состав архива

```
bridge_20261116_040000.tar.gz          (или .tar.gz.enc при BACKUP_PASSWORD)
├── MANIFEST.json                      # версия схемы/моста, состав, счётчики
├── db/bridge.db                       # КОНСИСТЕНТНЫЙ дамп SQLite
└── profiles/
    ├── account_1/Default/Cookies      # живые сессии MAX: Cookies,
    ├── account_1/Default/Local Storage/…   Local Storage, IndexedDB,
    └── account_2/…                    # Session Storage — всё на месте
```

Из архива **исключены** регенерируемые папки Chromium: `Cache`, `Code Cache`,
`GPUCache`, `DawnCache`, `ShaderCache`, `Crashpad`, `blob_storage`,
`Service Worker`, `component_crx_cache`, `Safe Browsing` и др. (полный список
— `EXCLUDED_DIRS` в [`app/backup.py`](app/backup.py)), а также лок-файлы
живой сессии (`SingletonLock/Socket/Cookie`, `LOCK`, `DevToolsActivePort`).
Типичный архив 2–5 аккаунтов весит 1–5 МБ.

Дамп БД делается через `sqlite3.Connection.backup()`, а не копированием
файла: copy main-файла без `-wal` теряет последние транзакции и иногда даёт
побитый файл. Дамп проверяется `PRAGMA quick_check` до упаковки.

### Когда и куда

* **Суточно** — фоновая задача `backup_scheduler` в `BACKUP_HOUR` (по
  умолчанию **04:00**, после плановых ночных релоадов страниц в 03:00+N*7 мин).
  Падение планировщика мост не роняет: лог + уведомление админу.
* **Вручную** — `/admin → 💾 Бэкап сейчас` или команда `/backup`.
* **Локально** — `/data/backups/` (том `./data/backups`), ротация: последние
  `BACKUP_KEEP` (по умолчанию 7) копий, остальные удаляются.
* **В Telegram** — архив отправляется документом супер-админу через наш же
  Nginx-прокси с подписью (дата, размер, активные аккаунты, слушатели,
  список профилей). Ограничение Bot API на загрузку — **50 МБ**: при
  превышении архив остаётся на диске, а бот шлёт путь и предупреждение.
  Порог настраивается `BACKUP_SEND_MAX_MB` (выше 50 не поднимается).

### Шифрование

`BACKUP_PASSWORD` (в `.env`, `chmod 600`) включает `openssl enc -aes-256-cbc
-pbkdf2 -salt`: внутри лежат **живые сессии MAX**, и незашифрованный архив,
уплывший куда-то кроме этого диска, равен утечке аккаунта. Пароль передаётся
подпроцессу через переменную окружения, а не argv — не светится в `ps`.
Если openssl вдруг нет в образе — бэкап делается незашифрованным и в отчёте
явно возвращается предупреждение (тише воды, чем молчаливая потеря).

### Восстановление

```bash
# осмотреть архив, ничего не трогая
docker compose run --rm bridge python scripts/restore.py \
    /data/backups/bridge_20261116_040000.tar.gz --inspect

# dry-run: распаковать во временную папку и показать дерево
docker compose run --rm bridge python scripts/restore.py bridge_20261116_040000.tar.gz

# боевое восстановление (сначала остановить мост!)
docker compose down
docker compose run --rm bridge python scripts/restore.py \
    /data/backups/bridge_20261116_040000.tar.gz.enc \
    --password "$BACKUP_PASSWORD" --data-root /data --apply
docker compose up -d
```

`restore.py` по умолчанию **ничего не перезаписывает**: существующая БД
сохраняется как `bridge.db.pre-restore-<ts>`, существующие профили
пропускаются (чтобы затереть — `--clean-existing`). Экстракция защищена от
path traversal (`../`, абсолютные пути, симлинки наружу, спецфайлы).
Восстановление профиля на другой машине обычно безопасно: Chromium сам
мигрирует формат, но если MAX сочтёт сессию подозрительной — аккаунт попросит
переавторизацию, это штатный путь (`/admin → 🔑 Переавторизовать`).

## 13. Сборка: две частые инфраструктурные ошибки (v2.2.1)

Обе не имеют отношения к коду приложения — это среда хоста. Команда диагностики
(ничего не меняет, только читает):

```bash
sh scripts/doctor.sh          # + --smoke для пробного mini-build
```

### «exec /bin/sh: exec format error» (обычно на x86-хосте)

**Причина:** buildx собирает образ **чужой архитектуры** — arm64-бинарники на
x86-ядре. Типовой сценарий: прежняя версия compose пиннул `platform: linux/arm64`,
arm64-вариант базового образа осел в кэше под тем же тегом, и последующие сборки
переиспользуют его (поэтому слой `WORKDIR` показывает `CACHED`, а падает первый
же `RUN`).

**Лечение (v2.2.1):** платформа в compose теперь **пустая по умолчанию** — берётся
нативная архитектура хоста (на плате arm64, на ноутбуке amd64):

```bash
# обычная сборка — нативная арх хоста, без QEMU:
docker compose up -d --build

# если образ-«инок» уже в кэше:
docker image rm mcr.microsoft.com/playwright/python:v1.49.0-jammy
docker compose up -d --build

# кросс-сборка arm64 на x86 (для переноса на плату) — нужен QEMU ОДИН РАЗ:
docker run --privileged --rm tonistiigi/binfmt --install arm64
BRIDGE_PLATFORM=linux/arm64 docker compose up -d --build
```

Проверьте также, что нигде не задана `DOCKER_DEFAULT_PLATFORM=linux/arm64`
(~/.bashrc, systemd-юниты) — она форсирует платформу поверх compose (doctor.sh
ловит и это).

### «failed to mount … operation not permitted» (типично на Orange Pi / SBC)

**Причина:** демон Docker работает **rootless** (путь `/home/<user>/.local/share/docker`
в сообщении об ошибке — верный признак), а монтирование overlay внутри user
namespace запрещено на многих SBC-ядрах (Rockchip BSP 5.10, старые AppArmor).
Код образа тут ни при чём — падает даже `WORKDIR`.

**Лечение по убыванию сложности:**

1. **Перейти на rootful-демон (рекомендуется для платы):**
   ```bash
   sudo systemctl disable --now docker@$(id -u)   # остановить rootless-сессию
   sudo systemctl enable --now docker              # системный демон
   sudo usermod -aG docker $USER                  # перелогин
   docker info --format '{{.DockerRootDir}}'      # должно стать /var/lib/docker
   ```
2. Если нужен rootless — **выключить containerd image store**:
   `{"features": {"containerd-snapshotter": false}}` в
   `~/.config/docker/daemon.json`, затем `systemctl --user restart docker`.
3. Разрешить unprivileged userns (ядро/AppArmor):
   ```bash
   sudo sysctl -w kernel.unprivileged_userns_clone=1        # Debian-подобные
   sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0  # Ubuntu 24+
   # закрепить в /etc/sysctl.d/99-docker.conf
   ```
4. `docker compose up -d --build` заново.

### Устранён дополнительный источник отказов сборки

Раньше Dockerfile **обязательно** выполнял `apt-get update && apt-get install
openssl x11vnc` — сетевой слой, который падал на кривых зеркалах/DNS/прокси
домашних сетей. Теперь:

* `openssl` **уже есть** в базовом jammy-образе (шифрование бэкапов работает
  без установки; doctor.sh проверяет это внутри образа);
* `x11vnc` ставится только по запросу:
  `docker build --build-arg INSTALL_VNC=1 -t max-tg-bridge:2 .` — он нужен
  лишь для опции ручной капчи через VNC.

Боевая сборка теперь не требует сети вообще, кроме pip (PyPI) и pull базового
образа (mcr.microsoft.com).

## 14. Селекторы и отладка

* Все селекторы — в [`app/selectors.py`](app/selectors.py) (как в v1, гайд
  DevTools внутри файла). Логи теперь **на аккаунт**: `data/logs/browser_a<N>.log`,
  скриншоты авторизации `data/logs/auth_a<N>_*.png`.
* Мост чтения (`_JS_BRIDGE`) не менялся и по-прежнему покрыт тестом:
  `bash tests/run_js_bridge_test.sh`.
* Быстрая диагностика:

| Симптом | Действие |
|---|---|
| 🔴 «требуется авторизация» | /admin → Переавторизовать (или кнопка из уведомления) |
| чат не открывается после входа | скриншот `auth_a<N>_*` + селекторы `SEARCH_*`, `CHAT_ITEM`, `CHAT_SCOPE` |
| «Поле ввода телефона не найдено» | бот сам переключается с QR-экрана (`PHONE_SWITCH`); если не вышло — скриншот `auth_a<N>_no_phone_input_*.png` и обновите `PHONE_SWITCH`/`PHONE_INPUT` |
| дубли/молчание ленты | `seed=` в `browser_a<N>.log`, затем `CHAT_SCOPE`/`MESSAGE_TEXT` |
| кто-то из слушателей «пропал» | он не нажал /start боту или заблокировал — добавление слушателя предупреждает, но проверить стоит |
| OOM / SIGBUS Chromium | не уменьшайте `shm_size: '4gb'`; проверьте `docker stats` |
| фолбэк-логины | `python -m app.auth --account <id> --manual` + VNC |

Логи: `docker compose logs -f bridge`; пер-аккаунтные: `tail -f data/logs/browser_a2.log`.

## 15. Безопасность

* `.env` (токен бота, `ADMIN_TG_ID`, резидуальные телефоны) — `chmod 600`,
  в `.gitignore`, попадает в контейнер только через `env_file`.
* Профили Chromium = живые сессии MAX — каталог `data/` наружу не отдаём,
  бэкапы шифруем. `ADMIN_TG_ID` — единая точка власти; компрометация этого
  аккаунта Telegram = компрометация всех аккаунтов MAX. Бот-приглашения
  слушателей не дают никаких прав на запись.
* VNC — только bind на `127.0.0.1` + SSH-туннель + пароль, только на время
  ручной капчи.
* Удаление аккаунта не уничтожает профиль сразу — он переезжает в
  `data/profiles/.trash/` (ручная зачистка).

## 16. Известные ограничения

* Ответы Слушателей не буферизуются «на потом, станет владельцем» — право
  ответа неотчуждаемо от аккаунта.
* Reply через контекстное меню MAX — best-effort: при смене верстки меню
  деградирует до обычного сообщения с цитатой.
* Редактирования/удаления в MAX не транслируются; голосовые/видео/файлы —
  не пересылаются (расширяется по образцу картинок).
* Интерактивная FSM авторизации живёт в памяти процесса: рестарт контейнера
  посреди ввода кода прерывает сессию (аккаунт останется в 🔑/🔴, кнопка
  «Переавторизовать» перезапускает сценарий).
* MAX не имеет официального Bot API — это UI-автоматизация вашего аккаунта;
  редкие просьбы войти по коду — норма, профиль сводит их к минимуму.
* Бэкап — не репликация: архив это снапшот, а не потоковая копия. Между
  ночными запусками окно потери — до суток (плюс ручная кнопка `/backup`).
  Доставленный в Telegram архив шифруется только при заданном
  `BACKUP_PASSWORD`; без пароля архив улетает наружу в открытом виде.
* Восстановление профиля на другой машине/архитектуре обычно работает, но
  MAX может счесть сессию подозрительной и попросить переавторизацию —
  данные при этом не теряются.
