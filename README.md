# MAX ⇄ Telegram Bridge v2 — Multi-Account & Role-Based

Мост между веб-клиентом мессенджера **MAX** (`https://web.max.ru`) и
**Telegram** для школьных чатов. Версия 2.0 переносит управление аккаунтами
и правами **внутрь Telegram-бота**: админ добавляет аккаунты MAX, ведёт
интерактивную авторизацию (со скриншотами страницы прямо в чат бота),
назначает Владельцев и Слушателей — без консоли, файлов конфигов и рестартов.

```
                         домашний резидентный IP (MAX — без прокси!)
                                        │
 Orange Pi 5 Plus (arm64, Docker, 32GB) │
 ┌───────────────────────────────────────┴──────────────────────────────┐
 │  max-tg-bridge v2 (python asyncio, один контейнер)                   │
 │                                                                      │
 │  AccountManager (супервизор, изоляция падений)                       │
 │  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐                │
 │  │ Worker acct1 │  │ Worker acct2 │  │ Worker acctN │  each: own     │
 │  │ Chromium+ctx │  │ Chromium+ctx │  │ Chromium+ctx │  profile dir,  │
 │  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘  own tasks     │
 │         │   JS-мост ленты │   (blob/fetch)  │                        │
 │         └────────┬────────┴────────┬────────┘                        │
 │                  ▼                 ▼                                 │
 │            SQLite v2         TelegramCore (aiogram v3)               │
 │        роли/аккаунты/          long-polling                          │
 │        fanout-map              строго через TG_API_BASE ─────────────┼──► Nginx ─► api.telegram.org
 └──────────────────────────────────────────────────────────────────────┘
```

### Что нового в 2.0

| Возможность | Как |
|---|---|
| **2–5 изолированных аккаунтов MAX** | у каждого свой `launch_persistent_context` в `/data/profiles/account_<id>/`, свой Chromium-процесс и свой набор asyncio-задач |
| **Роли** (SQLite) | Супер-админ (`ADMIN_TG_ID`), **Владелец** аккаунта (1-к-1, двусторонняя связь), **Слушатели** (read-only) |
| **Фан-аут сообщений** | каждое сообщение MAX уходит в ЛС Владельцу и каждому Слушателю; для каждого — своя запись `message_map`, поэтому reply Владельца резолвится именно в свой исходник |
| **Авторизация через бота (FSM)** | добавление/переавторизация аккаунта прямо в диалоге с ботом; после телефона и кода бот шлёт **скриншот страницы** — сразу видно, капча или код принят |
| **Уведомления о севших сессиях** | ночью сессия протухла → админу сообщение с кнопкой «🔑 Переавторизовать <имя>», той же кнопкой стартует FSM поверх сохранённого профиля |
| **Изоляция отказов** | падение/разлогин одного аккаунта не касается остальных; авто-перезапуск с backoff |
| **Разнесённые ночные перезагрузки** | аккаунт N стартует мягкий reload в `03:00 + N*7 минут` |

Сетевая идеология v1 сохранена: **MAX — всегда напрямую** (резидентный IP —
«обычный юзер», дата-центровый прокси = флаг антифроду); **Telegram — только
через `TG_API_BASE`** (`TelegramAPIServer.from_base` + собственный Nginx).

## 2. Ролевая модель

| Роль | Кто | Права |
|---|---|---|
| **Супер-админ** | `ADMIN_TG_ID` из `.env` (единственный) | `/admin`: добавлять/запускать/останавливать/удалять аккаунты, вести авторизацию, назначать владельцев и слушателей, статус системы. Сам может одновременно быть и владельцем/слушателем аккаунтов |
| **Владелец** | `accounts.owner_tg_id`, ровно один на аккаунт | получает всё из чата MAX в ЛС; **может отвечать**: reply на пересланное (уходит реплеем/цитатой в MAX) или `!макс текст`; фото — приложением |
| **Слушатели** | строки таблицы `listeners` | только чтение: получают копию входящих; на их попытки отвечать — вежливая заглушка «у вас режим только чтение» (не чаще раза в 5 минут) |

Правило ответа: reply резолвится через `message_map(tg_message_id)` →
аккаунт + превью исходника; отвечать может только `owner_tg_id` этого
аккаунта. У владельца с несколькими аккаунтами `!макс …` спрашивает,
в какой из них отправить (inline-кнопки).

## 3. Деплой (с нуля)

```bash
git clone <repo> && cd max-tg-bridge
cp .env.example .env && nano .env      # TG_BOT_TOKEN, TG_API_BASE, ADMIN_TG_ID
chmod 600 .env
mkdir -p data/{profiles,state,tmp,logs}

docker compose up -d --build
docker compose logs -f bridge
```

Nginx-реверс Telegram API — как в v1, конфиг в
[`nginx/telegram-api.conf.example`](nginx/telegram-api.conf.example)
(проксируются `/bot…` и `/file/bot…`, `proxy_ssl_server_name on`,
`Host: api.telegram.org`).

Первый запуск без аккаунтов: бот жив, `/admin` показывает пустую панель.

## 4. Первый аккаунт — из Telegram, без консоли

1. Админ пишет боту `/admin` → **➕ Добавить аккаунт MAX**.
2. Бот спрашивает по очереди:
   - **имя профиля** («Школа 5Б»);
   - **название чата в MAX** (можно и прямую http-ссылку на чат);
   - **Telegram ID Владельца** (число или `me` = сам админ).
3. Бот создаёт аккаунт, поднимает изолированный Chromium, открывает
   `web.max.ru` и просит **номер телефона** — админ присылает его в чат.
4. Бот вводит номер, жмёт «Далее» и **присылает скриншот страницы**: видно,
   что кодовое поле появилось / вылезла капча / уехал QR.
5. Админ присылает **код из СМС** → бот вводит → снова скриншот → бот ждёт
   входа (до 90 c), открывает целевой чат по названию, закрывает браузер
   входа, помечает аккаунт 🟢 и поднимает воркер. Готово — сообщения пошли
   Владельцу в ЛС.
6. Слушатели: `/admin → аккаунт → 👥 Слушатели → ➕` и «`123456789 Папа Маши`».
   Слушателю прилетит приглашение запустить бота.

Ввод «отмена» на любом шаге аккуратно сворачивает сессию (новый аккаунт
полностью откатывается; переавторизация оставляет аккаунт в 🔴).

### Капча / QR

Если после телефона или кода на скриншоте видна капча/QR, бот даёт кнопку
инструкции и «Повторить код». Автоскрипт картинки не разгадывает.
Чтобы пройти её глазами:

1. В `docker-compose.yml` раскомментируй Xvfb/VNC-блок (`entrypoint:
   ["/usr/local/bin/xvfb-start.sh"]`, `VNC_ENABLE=1`, порт `127.0.0.1:5900`),
   поставь `.env` `MAX_HEADLESS=false`.
2. `docker compose up -d bridge`, повтори «Переавторизовать» в боте.
3. `ssh -L 5900:127.0.0.1:5900 pi@опи` → VNC-клиент на `localhost:5900`
   (пароль из `VNC_PASSWORD`) — перед глазами настоящий Chromium, проходится
   мышкой. После — вернуть compose в боевой вид.
   (Альтернативы: noVNC-контейнер; `ssh -X` с пробросом X11-сокетов — см. ниже
   «Отладка».)

### Севшая сессия ночью

Воркер любого аккаунта при детекте разлогина: статус `auth_required`,
уведомление админу «🔴 Сессия MAX аккаунта <имя> истекла» + кнопка
**«🔑 Переавторизовать»** → тот же FSM, но профиль (`data/profiles/account_N`)
сохранён: обычно достаточно свежего кода из СМС, телефон спрашивается только
при редком полном сбросе. Остальные аккаунты работают как ни в чём не бывало.

### Аварийный консольный вход (если Telegram-канал сам недоступен)

```bash
docker compose run --rm bridge python -m app.auth --list
docker compose run --rm bridge python -m app.auth --create "Школа 5Б" --chat "9 Б" --owner 123456789
docker compose run --rm bridge python -m app.auth --account 3 --manual
```

## 5. Миграция с v1

```bash
# 1) обновить код до v2, .env дополнить ADMIN_TG_ID;
#    старые строки TG_CHAT_ID / MAX_CHAT_TITLE / MAX_CHAT_URL / MAX_SELF_NAME
#    ВРЕМЕННО оставить — скрипт использует их как сид первого аккаунта
docker compose run --rm bridge python scripts/migrate_v1.py --dry-run
docker compose run --rm bridge python scripts/migrate_v1.py
docker compose up -d --build
```

Скрипт идемпотентен и делает три вещи:

1. **SQL** (`store.py` сам, при открытии базы v1): `seen_message`/`msg_map`
   переносятся в «аккаунт-наследник №1» (схема —
   [`migrations/0002_role_based_multiaccount.sql`](migrations/0002_role_based_multiaccount.sql));
2. **ENV-сид**: имя/чат/владелец/анти-эхо аккаунта из строк v1
   (`TG_CHAT_ID` становится Владельцем; групповой чат v1 → id личного
   аккаунта менять не надо, просто добавьте нужных людей слушателями);
3. **Файлы**: `data/chrome_profile/` переезжает в
   `data/profiles/account_1/` — живая сессия MAX сохраняется; сообщения
   пойдут сразу, авторизация обычно не требуется вовсе.

После проверки удалите legacy-строки из `.env`. Ответы из старого общего
чата v1 не мигрируют: reply-маппинг привязан к личным диалогам v2.

## 6. Схема БД (v2, user_version=2)

```sql
accounts(id, name UNIQUE, phone, max_chat_title, max_chat_url, max_self_name,
         owner_tg_id, status, profile_path, created_at, updated_at)
listeners(id, account_id FK→accounts ON DELETE CASCADE, tg_user_id, alias,
          created_at, UNIQUE(account_id, tg_user_id))
message_map(id, account_id FK, tg_user_id, tg_message_id UNIQUE,
            max_message_key, max_sender, max_preview, created_at)
seen_message(account_id, key, first_seen, PRIMARY KEY(account_id, key))
stats(account_id, name, value, PRIMARY KEY(account_id, name))
meta(k, v)
```

`message_map` — критичная таблица фан-аута: один текст из MAX порождает N
telegram-сообщений (Владелец + Слушатели), у каждого свой `tg_message_id`;
именно поэтому ключ карты — **на** сообщение от бота, а владелец резолвится
по нему обратно к `max_message_key` и превью для реплея в MAX.
Полная история версий — в справочном SQL-файле `migrations/`.

## 7. Админ-панель (/admin)

```
/admin
├── 🟢 Школа 5Б / 🔴 Кружок робототехники / ⏸ …   (иконка статуса)
├── ➕ Добавить аккаунт MAX
└── 📊 Системный статус

аккаунт:
├── ▶️ Запустить          ⏸ Остановить
├── 🔑 Переавторизовать   👤 Сменить Владельца
├── 👥 Слушатели (N)      🗑 Удалить (двухшаговое подтверждение,
│                          профиль — в data/profiles/.trash/, не delete)
└── 📊 статус: аптайм воркера, MAX→TG (фото), TG→MAX, ошибки
```

«Системный статус»: аптайм моста, RAM контейнера из cgroup (используется/
лимит), число активных Chromium, счётчики каждого аккаунта.

## 8. Как пользоваться Владельцу/Слушателю

| Действие | Кто | Результат |
|---|---|---|
| Сообщение в чате MAX | все получатели | в ЛС: `👤 Мария Ивановна · 12.11 15:03` + текст; фото — подписанным `send_photo` (до 4 шт., последовательно) |
| **Reply** боту на сообщение из MAX | только Владелец аккаунта-источника | в MAX: «ответ» на исходное сообщение (best-effort меню) или цитата «…» + ответ |
| `!макс текст` / фото с префиксом | только Владелец | обычное сообщение в MAX (при нескольких аккаунтах — кнопка выбора) |
| Любой ответ | Слушатель | «у вас режим только чтение» (throttled) |
| `/start`, `/id`, `/help` | все | свои роли и id |

Эхо-защита от петли: собственные сообщения не пересылаются (mine-маркеры,
`max_self_name`, окно хэшей исходящих 90 с).

## 9. Офлайн-верификация

Всё хрупкое (роутеры, миграция БД, фан-аут, супервизор) покрыто прогоном без
браузера и без установленного aiogram/playwright:

```bash
python3 .verify/run_checks.py     # 12 проверок, exit 0 = всё зелёное
bash tests/run_js_bridge_test.sh  # JS-мост чтения на мини-DOM (node)
```

`run_checks.py` поднимает заглушки зависимостей, регистрирует цепочку
роутеров auth→admin→user, гоняет e2e-миграцию v1→v2 с переносом профиля,
проверяет фан-аут/дедуп/эхо-петлю в AccountWorker и жизненный цикл
AccountManager (включая переезд профиля в `.trash/`). Гоняйте после любой
правки store/bridge/account_manager/tg.

## 10. Селекторы и отладка

* Все селекторы — в [`app/selectors.py`](app/selectors.py) (как в v1, гайд
  DevTools внутри файла). Логи теперь **на аккаунт**: `data/logs/browser_a<N>.log`,
  скриншоты авторизации `data/logs/auth_a<N>_*.png`.
* Мост чтения (`_JS_BRIDGE`) не менялся и по-прежнему покрыт тестом:
  `bash tests/run_js_bridge_test.sh`.
* Быстрая диагностика:

| Симптом | Действие |
|---|---|
| 🔴 «требуется авторизация» | /admin → Переавторизовать (или кнопка из уведомления) |
| чат не открывается после входа | скриншот `auth_a<N>_*` + селекторы `SEARCH_*`, `CHAT_ITEM`, `CHAT_SCOPE` |
| дубли/молчание ленты | `seed=` в `browser_a<N>.log`, затем `CHAT_SCOPE`/`MESSAGE_TEXT` |
| кто-то из слушателей «пропал» | он не нажал /start боту или заблокировал — добавление слушателя предупреждает, но проверить стоит |
| OOM / SIGBUS Chromium | не уменьшайте `shm_size: '4gb'`; проверьте `docker stats` |
| фолбэк-логины | `python -m app.auth --account <id> --manual` + VNC |

Логи: `docker compose logs -f bridge`; пер-аккаунтные: `tail -f data/logs/browser_a2.log`.

## 11. Безопасность

* `.env` (токен бота, `ADMIN_TG_ID`, резидуальные телефоны) — `chmod 600`,
  в `.gitignore`, попадает в контейнер только через `env_file`.
* Профили Chromium = живые сессии MAX — каталог `data/` наружу не отдаём,
  бэкапы шифруем. `ADMIN_TG_ID` — единая точка власти; компрометация этого
  аккаунта Telegram = компрометация всех аккаунтов MAX. Бот-приглашения
  слушателей не дают никаких прав на запись.
* ВNC — только bind на `127.0.0.1` + SSH-туннель + пароль, только на время
  ручной капчи.
* Удаление аккаунта не уничтожает профиль сразу — он переезжает в
  `data/profiles/.trash/` (ручная зачистка).

## 12. Известные ограничения

* Ответы Слушателей не буферизуются «на потом, станет владельцем» — право
  ответа неотчуждаемо от аккаунта.
* Reply через контекстное меню MAX — best-effort: при смене верстки меню
  деградирует до обычного сообщения с цитатой.
* Редактирования/удаления в MAX не транслируются; голосовые/видео/файлы —
  не пересылаются (расширяется по образцу картинок).
* Интерактивная FSM авторизации живёт в памяти процесса: рестарт контейнера
  посреди ввода кода прерывает сессию (аккаунт останется в 🔑/🔴, кнопка
  «Переавторизовать» перезапускает сценарий).
* MAX не имеет официального Bot API — это UI-автоматизация вашего аккаунта;
  редкие просьбы войти по коду — норма, профиль сводит их к минимуму.
