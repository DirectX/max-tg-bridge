Ты — Senior Python Developer и архитектор асинхронных систем. У нас уже есть рабочий прототип однопользовательского моста `max-tg-bridge` (Python 3.11+, `asyncio`, `playwright`, `aiogram` v3.x, SQLite, Docker на Orange Pi 5 Plus `linux/arm64` с кастомным Nginx-прокси `TG_API_BASE`).

Твоя задача — спроектировать и реализовать **версию 2.0 (Multi-Account & Role-Based Bridge)**, которая переносит управление аккаунтами MAX и правами доступа внутрь самого Telegram-бота.

### 1. Ролевая модель и права доступа
В системе вводятся три четкие роли (хранятся в SQLite):
1. **Супер-администратор (`ADMIN_TG_ID` в `.env`):**
   - Единственный пользователь, имеющий доступ к админ-панели бота (`/admin` или inline-меню).
   - Может добавлять, запускать, останавливать и удалять аккаунты MAX.
   - Может назначать для каждого аккаунта MAX его **Владельца (Owner)** и список **Слушателей (Listeners)**.
   - Сам админ может быть как просто техническим администратором (не привязанным ни к одному аккаунту MAX), так и владельцем/слушателем одного из аккаунтов.
2. **Владелец аккаунта MAX (`Owner` — привязан 1-к-1 к конкретному инстансу аккаунта MAX):**
   - Получает все входящие сообщения (текст + фото) из отслеживаемого чата своего аккаунта MAX в личные сообщения с ботом (или выделенный приватный чат/топик).
   - **Имеет право двусторонней связи:** может отвечать (Reply) на пересланные сообщения или использовать префикс `!макс`, и бот отправит этот ответ (текст/фото) в MAX от имени его аккаунта.
3. **Слушатели (`Listeners` — список `tg_user_id`, привязанный к конкретному аккаунту MAX):**
   - Пользователи, которых админ добавил к конкретному аккаунту MAX.
   - **Только чтение (Read-Only):** получают копию всех входящих сообщений из MAX (текст + фото), но любые их попытки ответить (Reply) или написать боту игнорируются (или получают вежливую заглушку «У вас режим только чтения»).

### 2. Изоляция браузеров и управление воркерами
- Аккаунтов MAX будет немного (2–5 штук), на сервере 32 GB RAM.
- Каждый аккаунт MAX должен работать в **строго изолированном** процессе/контексте:
  - Собственная директория профиля: `/data/profiles/account_<id>/` (`launch_persistent_context`).
  - Собственный экземпляр `BrowserContext` / `Page` в Playwright со своими cookies, `localStorage`, `User-Agent` и изолированным состоянием (никакого пересечения данных между аккаунтами).
  - Независимая асинхронная задача (`asyncio.Task`) в менеджере воркеров (`AccountManager`): падение или разлогин одного аккаунта не должны ронять остальные.
  - Индивидуальная суточная мягкая перезагрузка страницы со сдвигом по времени (чтобы все браузеры не перезагружались в одну секунду).

### 3. Интерактивный GUI-less логин через Telegram-бота (FSM)
Нужно перенести логику консольного `auth.py` в машину состояний (`aiogram.fsm`) для администратора:
1. Админ нажимает «Добавить аккаунт MAX» в боте.
2. Бот запрашивает **название профиля** (например, «Школа 5Б»), **название целевого чата в MAX** и **Telegram ID Владельца (Owner)**.
3. Бот запускает изолированный Playwright-контекст для нового аккаунта, открывает `https://max.ru` и запрашивает у админа **номер телефона**.
4. Админ отправляет номер в чат боту → бот вводит его на странице MAX.
5. **Обработка капчи / QR (важно!):** Сразу после ввода номера (и после ввода СМС) бот делает скриншот страницы (`page.screenshot()`) и отправляет его админу в Telegram, чтобы админ видел, ушел ли код или появилась капча. Если появилась капча — бот дает админу ссылку/инструкцию на временный VNC или позволяет нажать кнопку «Повторить».
6. Бот запрашивает **код из СМС** → админ вводит код в чат боту → бот вводит его в браузер, дожидается загрузки чатов, находит нужный чат, сохраняет `chrome_profile` и запускает воркер моста в боевом режиме.
7. Если у любого работающего аккаунта ночью «протухнет» сессия, бот отправляет уведомление Админу с кнопкой «Переавторизовать аккаунт <Название>», запуская тот же FSM-сценарий поверх существующего профиля.

### 4. База данных (SQLite)
Спроектируй схему БД (`store.py`) с таблицами:
- `accounts`: `id`, `name`, `phone`, `max_chat_title`, `max_self_name`, `owner_tg_id`, `status` (`active`, `stopped`, `auth_required`), `profile_path`, `created_at`.
- `listeners`: `id`, `account_id` (FK), `tg_user_id`, `alias` (имя/заметка для админа).
- `message_map`: `id`, `account_id` (FK), `tg_user_id` (кому отправлено), `tg_message_id`, `max_message_key`, `created_at` — **критично**, так как одно сообщение из MAX теперь рассылается разным пользователям (Владельцу и Слушателям), и у каждого в Telegram будет свой `tg_message_id`, по которому Владелец сможет сделать Reply!

### 5. Команды и интерфейс админа в Telegram
Реализуй удобное меню на `InlineKeyboardMarkup` по команде `/admin`:
- **Список аккаунтов MAX:** статус (🟢 работает / 🔴 разлогинен / ⏸ остановлен), кнопки управления для каждого (Запустить / Остановить / Перелогинить / Удалить / Сменить Владельца).
- **Управление слушателями:** выбрать аккаунт MAX → посмотреть список `tg_user_id` слушателей → добавить слушателя (ввод ID) / удалить слушателя.
- **Общий статус системы:** аптайм, потребление RAM контейнером, количество активных браузеров, счетчики пересланных сообщений по каждому аккаунту.
